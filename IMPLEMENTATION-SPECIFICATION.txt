Update Flightdesk UK into a streamlined, browser-local workspace covering preparation, pre-flight briefing, in-flight recording and post-flight debriefing. 4. VLOS: FIXED SCOPE, NOT A REPEATED YES/NO QUESTION

Remove the routine 'Direct VLOS planned? Yes/No' dropdown from supported Open Category planning. Replace it with an explicit scope statement: 'Open Category planning: Visual Line of Sight (VLOS) operations only.' This is a scope constraint, not evidence the user has actually assessed the route.

Explain VLOS in plain language based on current CAA guidance: maintain the necessary direct unaided view of the aircraft and awareness of surrounding airspace; camera video alone does not establish VLOS; normal corrective spectacles/contact lenses are permitted. Do not invent a universal numeric VLOS distance or infer VLOS from the mission-area radius.

Include VLOS once in the consolidated final pre-flight declaration, for example: 'I have assessed the route and conditions, can maintain the applicable VLOS requirements throughout the flight, and have reviewed the remaining operational checks.' The exact wording must accommodate a properly supported FPV observer arrangement. Do not add another mandatory VLOS checkbox elsewhere.

Retain an optional operator-imposed distance limit with distance, basis/source and applicability. A distance entry does not establish VLOS. Invalidate the relevant confirmation when route/site, aircraft, distance restriction or other applicable conditions change.

Provide a clearly secondary 'My operation needs a different assessment / I cannot meet these conditions' route. BVLOS, unsupported Specific Category, Certified and association-authorised operations must be labelled OUTSIDE SUPPORTED SCOPE; preserve drafts/export but do not issue an assessed GO/WARNING or enable an assessed launch through this workflow. Link to CAA authorisation guidance. Entering an authorisation reference alone must not unlock BVLOS readiness. Specific Category is not synonymous with BVLOS: some authorised operations are VLOS but still outside this app's supported assessment.

If FPV is retained, conditionally request an observer arrangement and briefing acknowledgement only when applicable. Follow the CAA requirements for the observer's position, communication and direct view. An observer does not extend the supported operating range or turn BVLOS into VLOS. Do not implement EVLOS/BVLOS by distributing observers along a route.

For migration, an old explicit VLOS 'no/unsure' must not silently become supported VLOS. Preserve it as an unresolved scope issue until the user explicitly establishes a new supported plan. Historical records remain as recorded.

5. DATA MODEL AND PHASES

Separate persistent reusable entities from per-flight observations:
- Project and site profiles.
- Aircraft assets: model plus optional nickname, asset/serial identifier and stable ID.
- Payload/operating profiles linked to a compatible aircraft/configuration.
- Pilot/operator profiles and relevant competence/expiry records.
- Individual battery packs and matched-set membership.
- Missions grouping related work and individual sorties, each with a unique stable ID.
- Immutable pre-flight briefing revisions, flight events and post-flight/debrief revisions.

Keep model-level manufacturer specifications distinct from asset identity, pilot-validated configuration and measured current-flight values. Avoid copying manufacturer fields into user-owned data without provenance.

Use a clear lifecycle such as DRAFT -> READY or REVIEWED_WITH_WARNINGS -> AIRBORNE -> LANDED -> DEBRIEF_COMPLETE. Support cancellation/postponement before take-off and an explicit unresolved/recovery state after interruption. Derive readiness separately from lifecycle. A draft may be NO-GO; a landed flight is not 'NO-GO because its start time is in the past'. Do not use a single status variable for both safety readiness and phase.

Each take-off/landing pair is a sortie. Consecutive flights at one site share setup where appropriate, but have separate batteries/readings, actual times, declarations and outcome records.

6. REUSABLE SETUP AND WORKFLOW

Offer 'New mission', 'Use previous setup' and 'Next flight at this site' through one consistent mission-management surface. Define clearly whether each action saves a snapshot, applies an earlier setup or starts a new sortie. Never replace an unsaved draft silently.

On reuse, carry project/site, selected asset, compatible payload, crew, applicable limits and reference notes. Reset live battery readings, flight-phase events, actual times, weather/airspace validity and final launch declarations. Explicitly label carried notes as references requiring review. Reuse a recent valid briefing only if area, time window, height, source validity and permissions still cover the new sortie, and record its provenance; otherwise require fresh review.

Make the changed elements obvious. Use a brief 'What changed since the last flight?' summary rather than blanket-resetting unrelated checks. Save operating limits and supported endurance in named aircraft/payload profiles so users need not recreate them every flight. Applying a profile is a suggestion to review, not proof the current aircraft is configured accordingly.

Allow pilot and operator to refer to the same person without duplicate typing, while keeping their separate registration roles and expiry requirements.

7. CONSOLIDATE DECLARATIONS AND FIX INVALIDATION

Create one authoritative completion/readiness model consumed by form labels, section headings, navigation, decision cards, saves and exports. Do not infer correctness from colours, copied text or previously checked UI state.

Remove duplicate final checks already evidenced in crew/aircraft, battery, weather and airspace sections. Replace them with read-only status summaries linked to the originating checks. Keep one final operational declaration for the whole sortie. Preserve old checklist evidence when importing historical records.

Maintain distinct physical battery inspection, current controller readings and flight-time assumptions where their meaning differs. A warning acknowledgement is conditional and does not replace the normal review.

Ask about A2 competence only when relevant to the selected operating route; store reusable qualification information in the pilot profile. Do not erase a saved qualification when it is irrelevant to one mission.

Build explicit dependencies for each declaration. Revalidate configuration when mass, payload, aircraft/class, fitted battery configuration or covered limits change. Revalidate cell checks when relevant readings/criterion/set change. Revalidate weather/airspace only when their relevant scope or source validity changes. Unrelated notes, navigation, backup actions or checking another box must not untick confirmations.

Before resetting a confirmation, show or record why it became stale. A new physical inspection is different from revising a note. Test typing behaviour so re-rendering does not replace partially typed numbers or move focus.

8. PRE-FLIGHT INFORMATION AND ORDER

Use a coherent workflow: project/site/scope -> crew and aircraft/payload -> weather and airspace -> equipment/controller/batteries -> consolidated readiness -> save briefing/start flight.

Retrieve weather and NOTAMs before endurance is complete. Explain the interval currently assessed, then update weather coverage when the calculated allowance becomes available. Replace the fixed +/-2-hour NOTAM filter with the operating-session briefing window specified in section 9, still independent of battery calculation. Once a supported flight interval is known, verify it is fully covered and require an extended/reviewed briefing when necessary. Preserve historical windows exactly as recorded.

Keep critical inputs visibly distinct from optional information. Use short inline explanations, with details/examples collapsed. Keep scope, active warnings, unresolved issues and storage state visible. Do not impose an extra acknowledgement for every explanatory paragraph.

9. AIRSPACE, NATS AND SESSION-BASED NOTAM REVIEW

Replace the existing fixed +/-2-hour rule. This revision explicitly supersedes earlier instructions to preserve that fixed window. NOTAMs may be published, replaced or cancelled at short notice; they are not a once-daily product. The relevant question is whether an applicable notice's validity/activity overlaps the operating area, vertical envelope and flight interval, not whether it was published within the last two hours. Include relevant long-running notices issued days or weeks earlier.

9.1. Operating session and briefing interval

Use one operating-session record for repeated flights at a site, linked to its sorties. Reuse the existing selected date and estimated take-off time as the initial session start; do not make the user enter that start twice. Offer a compact session-end date/time that can be extended and handles crossing midnight. If the end is not known, suggest start plus two hours as an explicitly labelled, editable assumption; never imply it was confirmed or is a regulatory limit. Show the resulting absolute dates/times rather than an ambiguous 'next two hours'.

Default the screening interval to 30 minutes before the session start until 30 minutes after its planned end. Label this as an app planning buffer, not a CAA-prescribed period. Permit a documented operator/profile adjustment without adding two routine mandatory fields. Example: site session 10:00-13:00; screening 09:30-13:30. Do not require users to repeat this setup for each battery change.

Do not delay retrieval until mission duration/endurance is calculated. As the plan becomes more definite, check every sortie's entire take-off-to-landing and contingency interval against the reviewed session coverage. A flight outside that coverage, or a change of site/route, height or operating envelope, requires an expanded or new briefing. Expanding the end must never silently mark new hours reviewed. On the next day/site session, require the appropriate new review rather than treating yesterday's brief as current.

Store UTC instants and display Europe/London with the offset and date where needed. NOTAM UTC times and London local times must not be compared as raw strings. Test BST/GMT, ambiguous/nonexistent local times, midnight and multi-day validity. Clearly distinguish session start/end from flight take-off time and forecast sample time.

9.2. Freshness, coverage and publication are separate

Display and preserve separately: request/download time; source collection generation/issue time; source/provenance (normal official briefing, official contingency collection or independent archive); supplier's documented/declared coverage; user-reviewed operating interval and review time; latest before-flight check time; relevant changes since review.

A recent HTTP response is not proof of a recently generated or complete collection. A generated-at timestamp is not a notice's activation time. Do not filter solely on notice issue time, age of the download, or 'today'. Do not infer collection completeness from the latest expiry of any one notice or the absence of matching notices. Record unknown coverage honestly and distinguish source-declared coverage from a documented supplier coverage assumption.

The existing NATS contingency PIB collection is published hourly and described as covering current notices and the following seven days; it is supplementary, not a live operational briefing service. Confirm the current documented feed behaviour at implementation. Show its expected cadence. A repeat download returning the same collection can be a successful check with no new data, not a failed request. Conversely, repeated successful downloads must not refresh the apparent source age or cure an old/incomplete collection. Any age/late-update threshold must be a disclosed app/operator policy, not presented as a CAA legal freshness limit or guarantee that no new restriction exists.

The normal official NATS AIS briefing facility uses current briefing data and must be linked prominently for independent point/zone briefing. Do not automate authenticated access, scrape around access restrictions or add a paid subscription connection. Retain a documented fallback to official contingency sources and clearly identify any independent archive. A mirror's retrieval time never proves official currency.

9.3. Checks at each phase and each sortie

Support advance planning using notices valid during the future session, then obtain/review the latest appropriate briefing on site. Before each take-off, offer a clear 'Check for changes before this flight' action and record its result. Check that the reviewed area/height/session still covers this sortie, source status is acceptable or independent official review is documented, and newly relevant changes have been reviewed.

Refresh on explicit request; modest background polling while the app is visible may help but must not replace the before-flight check or overload suppliers. Do not promise updates while a PWA is suspended/offline. Group concurrent requests and prevent old responses overwriting a newer site/session request. Do not require a new supplier generation timestamp every time the pilot checks between hourly publications.

For repeated flights with unchanged scope, retain the prior reviewed notice set and highlight only new, replaced, cancelled, newly active or otherwise newly relevant notices. Keep unchanged relevant notices accessible without demanding that the user re-enter the same note or re-tick multiple acknowledgements. Notice IDs, NOTAMN/NOTAMR/NOTAMC relationships, content and reviewed versions must be tracked; comparing only list length or text display order is insufficient. Disappearance from an incomplete feed is not proof of cancellation. Deduplicate without losing amendment history.

A delayed launch, changed operating envelope, expanded session, new applicable restriction, significant relevant amendment or loss of reliable coverage invalidates the affected review and explains why. Unrelated edits and an unchanged successful refresh must not erase unaffected declarations. Preserve the previous evidence for audit rather than overwriting it. A notice crossing into activity during the existing session must already be considered in the session review; make the upcoming activation visible.

During AIRBORNE, show detected relevant changes only as advisory information with the applicable emergency/operating-plan context. Do not force the pilot into screen interaction, remotely command the aircraft or imply the app provides continuous airspace surveillance. After landing, retain what was known/reviewed before take-off and append later observations or missed-change notes without rewriting history.

9.4. Relevance and interpretation

Retain conservative geographic/altitude screening over the full intended route/operating area, return and contingency area. Keep the search circle, actual route/area and optional VLOS distance distinct. A route/polygon tool is optional if reliable; retain a radius fallback. Map visibility toggles must not suppress assessment.

Evaluate interval overlap and activity schedules, including validity start/end, daily/repeated windows, PERM/estimated ends and cancellation/replacement where these are unambiguously supported. Link to the full notice and referenced AIC/Supplement/other documents. Do not attempt to automatically interpret unsupported free-text schedules as 'inactive'. Ambiguous schedules, unparsed location, unusual geometry or unclear limits must be retained for manual review with the uncertainty explained.

Distinguish AGL height, AMSL altitude and flight levels; require appropriate terrain context for any definitive vertical exclusion. Do not exclude every notice above 120 m or apply a simple launch-elevation assumption to the whole area. GNSS interference, hazards affecting the operation and relevant permissions may matter beyond a simple low-altitude restriction cylinder. Preserve excluded items with the reason/source and keep filtering testable. Clearly foreign advisories may be excluded only through defensible location/scope rules, not loose keyword matches.

Group the user-facing results: applicable/possibly applicable restrictions requiring attention; other relevant hazards/advisories; starts/changes during the session; unresolved-location/schedule items; reviewed unchanged notices; screened-out context. Distinguish a legal restriction/permission issue from a hazard advisory. Never use 'No NOTAMs' when retrieval failed or completeness is unknown. Prefer 'No potentially relevant notices found in the retrieved collection for [area/time], subject to the stated coverage limitations.'

9.5. Failure handling and independent official review

Preserve request states: never requested, pending, succeeded with new data, succeeded unchanged, failed, stale/incomplete and independently reviewed. Show when Refresh/check was pressed, processing outcome, source timestamps, coverage and reason for failure. Use one coherent notice before its relevant acknowledgement; avoid duplicated stale warnings.

Extend independent official-briefing evidence to missing/stale supplementary AIP/UAS reference layers as well as NOTAM failure. Record official source/reference, review timestamp, covered area/height/time window and permissions/actions. Allow a concise note plus an explicit pilot declaration rather than forcing multiple identical confirmations. Distinguish 'supplementary display unavailable, independently reviewed' from 'restriction unresolved'. A generic acknowledgement alone must never clear unresolved permission or restriction issues, missing required briefing evidence, or scope outside the review.

Keep the automated feed labelled failed/stale/incomplete even after the independent-review route is complete. A documented manual assessment can support the appropriate planning outcome; it must not turn that feed's status into 'current'. The pilot remains responsible for the briefing and permissions; do not represent the declaration as an independently verified clearance.

Do not hard-block a documented independent briefing solely because a supplementary map layer is unavailable, but continue to block an assessed start where relevant restrictions/permissions or actual operating limits remain unresolved. Preserve original data, source status and manual-review basis in the pre-flight snapshot, event log, export and post-flight record.

10. WEATHER, LIMITS AND ON-SITE OBSERVATIONS

Present a compact table of forecast values versus manufacturer/operator limits, identifying variable, units, interval, forecast value, limit, excess and source. Distinguish 10 m wind, gusts and 80 m wind; do not imply arbitrary flight-height wind is directly known.

Retain purple WARNING for acknowledged forecast exceedances in otherwise supported planning. Clarify that this means planning reviewed with unresolved forecast concern, not permission to exceed an operating limit. Actual adverse conditions, unresolved pilot assessment or a manufacturer fault must prevent an assessed take-off.

Add one concise on-site conditions review before launch. Optional observations can include measured wind/gust, approximate temperature/visibility, source and timestamp; do not force invented measurements or require specialist equipment without an operator procedure. Include rain, turbulence/terrain/buildings and ability to maintain VLOS. Record whether conditions are within limits, unacceptable or uncertain. Unacceptable/uncertain observations must not become GO by ticking awareness.

Support a traceable on-site reassessment when forecast concern exists; retain the original forecast warning even if the pilot records acceptable local observations. Do not fabricate a regulatory approval rule or accept arbitrary new limits.

Use green for completed inputs, orange for missing/stale evidence, purple for reviewed concerns, red for blockers and neutral for optional/unassessed items. Add text/icons so meaning does not depend on colour. A completed weather review can still carry a purple risk marker.

11. BATTERY MANAGEMENT AND ENDURANCE

Separate pack inventory, maintenance history, per-sortie inspection and current controller readings. Support individual pack IDs in a matched set, with migration from existing free-text set records without inventing constituent serial numbers.

Where pack count matters, validate a complete compatible fitted configuration. Do not treat an arbitrary larger inventory count as additional flight endurance. Record the lowest available charge for paired packs and retain per-pack values if supplied.

Manufacturer nominal cell voltage and derived charging ceiling remain read-only reference text. Do not prefill measured lowest/highest cells or take-off charge with nominal values. Distinguish model-specific criteria, general manufacturer maintenance guidance and operator-proposed criteria. Include their measurement conditions. Do not force a maintenance protocol to masquerade as a universal pre-flight test.

Determine from current manuals/app capabilities whether requested cell telemetry is available. If unavailable, support only a properly documented, applicable manufacturer/operator inspection method; do not offer 'not available' as a bypass for a known fault or required unresolved check. Explain unsupported configurations honestly.

Retain excessive-spread blocking, battery replacement flow, recorded failed readings, quarantine and replacement provenance. Treat operator/manufacturer repair-and-return-to-service decisions as explicit events; do not erase fault history or permanently blacklist a pack without a documented resolution path.

Rename the displayed duration to 'Estimated battery-based planning allowance (take-off to landing)' or an equally clear label. This explicitly supersedes the earlier 'maximum possible' wording. Calculate automatically from starting charge, conservative supported time to chosen landing reserve and extra contingency. Keep one physical reserve plus the separately explained time contingency; do not double-count either.

Show a simple calculation summary and assumptions. The manufacturer maximum is a sourced ideal-condition reference, not an accepted supported endurance value. Store validated profile assumptions for reuse. Do not imply that charge percentage is linear energy under all conditions or automatically invent wind/temperature derating. Keep optional actual-flight feedback for improving the user's conservative profile.

Include controller readiness/charge in equipment checks. Maintenance due dates/cycle counts are optional unless applicable procedures require them. A take-off is not automatically one full battery charge cycle.

12. IN-FLIGHT PHASE: TIMER AND EVENT LOG, NOT TELEMETRY

Implement an optional low-distraction in-flight panel. Label it 'Manual flight timer and event log — no live aircraft telemetry'. It must not claim to know location, charge, aircraft state, VLOS or link quality unless a separately verified integration actually supplies them. Do not add telemetry integration, drone control, background geolocation or account access in this implementation.

The normal assessed-start workflow must require an explicit user action and a complete supported briefing/on-site review. Save the pre-flight snapshot first; preserve GO/WARNING and its rationale at launch. For WARNING require its applicable review; acknowledgement alone cannot approve known unacceptable actual conditions. Explain launch recording as pilot-entered, not detected take-off. If app storage fails, offer a recoverable export path and clearly report that the event was not durably saved. Also provide a distinct 'Record an already-airborne / previously unrecorded flight' recovery route: factual event logging must remain possible even when no valid pre-flight assessment exists. Mark such a flight UNASSESSED or launched with unresolved items, retain the known NO-GO/out-of-scope evidence, and never fabricate a prior approval. This is factual recording, not an assessed-start bypass.

Display elapsed time, estimated remaining allowance, recorded landing reserve, pilot/operator/aircraft/pack identifiers, outstanding concerns and emergency-plan summary. Offer large, clearly labelled 'Record take-off', 'Record landing', 'Log event' and 'End/abort flight' actions appropriate to the current phase. Aborting records an intention/event, not proof of landing; require a landing time or explicitly unknown outcome.

Base elapsed time on persisted event timestamps, not counting interval callbacks. Record UTC instants, display Europe/London, handle date rollover/DST and detect implausible clock changes. Recover correctly after screen lock, background throttling, reload or app restart. Never silently invent take-off/landing times. If time is uncertain, label it and allow a documented correction. Do not pause airborne time because the UI was paused or backgrounded.

Persist events immediately with timestamps and actor/source. Offer optional quick events such as conditions changed, other aircraft observed, battery alert, loss of VLOS, lost link, return initiated, emergency or note. Event recording must not prescribe automatic RTH/landing instructions that ignore the operator's emergency plan. Never remotely command the aircraft.

Airborne operation must not force the pilot into a heads-down checklist. Encourage observer/ground-crew use or recording after landing. No routine mandatory screen interaction during flight. Optional alerts must be labelled best-effort: browser timers/audio/notifications can be suppressed and cannot replace aircraft warnings or pilot monitoring. Do not request notification permission automatically.

If the aircraft is already airborne when the app becomes stale/offline or a concern is recorded, preserve the phase and events. Display 'Airborne — reassess conditions / follow emergency plan' as appropriate, not a retrospective failed take-off form. No new GO may be issued from stale data. Continue the local timer/log offline when already started, while clearly marking live services unavailable. Offline drafts/logging remain possible; do not introduce an unreviewed offline launch-clearance pathway.

13. POST-FLIGHT DEBRIEF AND BATTERY HISTORY

After landing, offer a short debrief. Distinguish fields necessary to close a record from optional analytical details:
- Outcome: completed, partially completed, aborted, cancelled or postponed, with phase-appropriate semantics.
- Actual take-off/landing times and calculated duration, or explicitly missing/estimated values with explanation.
- Landing charge, preferably per fitted pack when available; optional pack temperatures/readings if supported.
- Defects, warnings, damage or incidents; an explicit 'Nothing to report' alternative.
- Follow-up actions, maintenance/quarantine status, lessons and optional mission deliverables/reference.

Record planned versus actual values without replacing the original briefing. Flight completion does not certify compliance. An incomplete debrief must remain savable; a critical defect can quarantine a battery/aircraft for subsequent sorties even if optional fields are empty.

Link each sortie to its actual asset and packs. Append usage/maintenance events rather than rewriting old history. Do not infer full charge cycles from flight counts. Returning a quarantined item to service requires a recorded decision/reference consistent with the applicable procedure.

Cancelled/postponed missions must not receive fabricated flight time or battery usage. Multiple take-offs require distinct sortie records. Keep pre-flight briefings, events and debrief revisions connected by stable IDs.

Provide project/site/day summaries and optional flight-time/battery-use summaries. Clearly distinguish planned maximum/allowance, recorded actual elapsed time, known data, estimates and missing values.

14. DRAFTS, SNAPSHOTS AND AUDITABILITY

Autosave unfinished drafts locally, separate from immutable saved briefing snapshots. Label the last successful save, dirty state and recovery option. A recovered draft must not restore expired declarations as current readiness. Re-evaluate relevant dependencies and freshness. Never lose an active-flight event log during draft recovery.

Avoid creating a new duplicate evidence snapshot for every keystroke. Keep intentional briefing revisions, event records and debrief revisions. Corrections must record what changed, when and why; preserve prior values. Local append-only application behaviour is not cryptographic tamper-proofing or a certified logbook. Exports must state that distinction.

Store app/build version, schema version, rules/catalogue review revisions, profile version, source timestamps and readiness/warning rationale with each relevant snapshot. Avoid storing unnecessary personal data or device identifiers.

15. STORAGE, MIGRATION AND LARGE BACKUPS

Eliminate the silent 300-entry truncation in inventory/history loading. Preserve existing records exactly. If capacity must be limited, warn before a write and provide an export/archive path without silently dropping entries. Handle browser storage quota/write failures visibly.

Choose a storage approach that reliably supports growing histories and atomic writes; IndexedDB is an option, not an excuse for a major unrelated rewrite. If migrating from localStorage, make migration versioned, transactional, resumable and idempotent. Verify integrity before retiring the old representation, and provide rollback/recovery. Do not auto-delete legacy data merely because migration started.

Support all-data export/import beyond the previous 10 MB trap: use a documented larger limit or safely split archives with a manifest and complete matching restore support. Reject malformed/oversized imports without partial loss. Repeated imports must not duplicate IDs. Do not execute imported content, trust imported readiness, permit prototype pollution or render imported text as HTML. Validate nested data and new phase/event fields.

Backups must include drafts/active-flight recovery data when explicitly labelled, immutable flight records, assets/profiles, batteries/sets/history, settings and provenance. Clearly distinguish saved records from drafts in backup and restore. Do not include API credentials. Restore into a fresh browser must work and must preserve historical GO/WARNING/NO-GO without treating them as current authorisation.

Retain backup-first Clear all app data under a collapsed menu. Require a current successful backup attempt, user confirmation of the completed file on disk, and final destructive confirmation. Include all new stores. Never delete or overwrite real user data in automated/browser testing.

16. PRIVACY AND SECURITY

Keep personal records browser-local by default. Do not introduce accounts, cloud synchronisation, telemetry, analytics, crash-report uploads or central record storage without explicit authorisation. Import means local file processing; make this clear.

Add concise privacy/storage information describing what stays local, location/postcode/map requests sent to providers, hosting connection metadata, retention/deletion, unencrypted backups and shared-device exposure. Do not promise zero privacy responsibilities, absolute privacy, encrypted-at-rest storage or that users cannot lose records. Obtain current official privacy guidance for statements about legal obligations; unresolved operator identity/contact details must be identified for the owner to complete rather than invented.

Maintain data minimisation. Use safe DOM text handling, appropriate HTTPS/security headers and tightly scoped external requests. Do not request or handle user weather API keys or subscription credentials. Ensure retired credential fields cannot be restored into active settings and that secrets remain excluded from logs, snapshots, drafts and exports. Do not change hosting access controls or DNS as part of this task.

17. PRESENTATION AND ACCESSIBILITY
